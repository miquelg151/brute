# Mobile Game UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the scrolling web pages into a mobile-game UI: a shell with top bar and bottom tabs (Fighter · Fight · Cards), a four-step creation with the fighter always visible, a one-screen pre-fight, and game feel (press buttons, transitions, celebration).

**Architecture:** `main.ts` keeps choosing full-screen moments from the save (creation, level-up, pre-fight, fight); when none applies it renders a new shell (`src/ui/shell.ts`) that hosts one of three tab modules (`src/ui/tabs/*.ts`). Existing pickers, stickers, card views and motion helpers are reused. A small optional `Character.deck` stores the preferred deck. A headless-Chrome screenshot tool verifies layouts at phone sizes.

**Tech Stack:** Vite + TypeScript, DOM via the `h()` helper (`src/ui/dom.ts`), CSS in `src/style.css` with tokens from `src/ui/theme.ts`, Phaser only for the fight replay, Vitest, Node 24 (built-in `WebSocket`/`fetch`) for the screenshot tool.

**Spec:** `docs/superpowers/specs/2026-10-24-mobile-ui-design.md`

## Global Constraints

- All game text and code comments in English; 2-space indent, single quotes, semicolons; plain-words comments; obvious code (the owner is a beginner and edits it).
- Keep the existing look: Shantell Sans only, sticker lettering tiers, paper cards, die-cut pixel stickers. No new fonts, no gradients/glossy "store game" styling, nothing that looks AI-generated or templated. Icons over words where an icon is clear.
- Colours and sizes come from `theme.ts` tokens / CSS variables so the owner can edit them in one place.
- Shell screens fit a 360 × 640 viewport without page scroll (only the Fighter and Cards tab bodies and a pre-fight mini-tab body may scroll inside themselves); respect `env(safe-area-inset-bottom)`. Tap targets ≥ 44 px.
- `prefers-reduced-motion: reduce` → no movement animations (fades at most).
- Every `localStorage`/`navigator.vibrate` access is guarded (try/catch or feature check).
- The fight simulation and its determinism are untouched; the save format only gains the optional `Character.deck`.
- Existing PNGs in `public/art` are never modified.
- Before every commit: `npx tsc --noEmit && npx vitest run && npm run build` green. UI tasks also run `npm run screens` (Task 1) and look at the shots they touch, at 360 × 640 and 390 × 844, with no console errors.
- Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never push, never touch `main`, never commit `captures/` or `screens/`.

`types.ts`, in `Character`: `/** The cards the player likes to bring (optional; see preferredDeck). */ deck?: string[];`

`game.ts`:

```ts
/** The deck brought by default: the saved one (owned cards only), topped up in card order. */
export function preferredDeck(c: Character): string[] {
  const deck: string[] = [];
  for (const id of [...(c.deck ?? []), ...c.cards]) {
    if (deck.length >= DECK_SIZE) break;
    if (c.cards.includes(id) && !deck.includes(id)) deck.push(id);
  }
  return deck;
}

/** Remembers the player's deck (owned cards only, no repeats, at most DECK_SIZE). */
export function setPreferredDeck(c: Character, ids: string[]): void {
  c.deck = ids.filter((id, i) => c.cards.includes(id) && ids.indexOf(id) === i).slice(0, DECK_SIZE);
}
```

`defaultTactics` uses `deck: preferredDeck(c)`. In `startFight`, after the deck is locked, call `setPreferredDeck(save.character, <the deck ids it locked>)`.

- [ ] **Step 5: Screenshot tool**

`tools/screens.ts` (run with `tsx`): launches the system Chrome headless (`C:/Program Files/Google/Chrome/Application/chrome.exe`; override with env `CHROME`), with `--remote-debugging-port`, a temporary `--user-data-dir`, `--headless=new`, `--hide-scrollbars`; connects with Node's built-in `WebSocket` to the page target from `http://127.0.0.1:<port>/json`; enables `Runtime`/`Page`; for each scenario and each size in `[[360, 640], [390, 844]]` sets `Emulation.setDeviceMetricsOverride` (`deviceScaleFactor: 2, mobile: true`) and touch emulation, runs the scenario's steps, and saves `Page.captureScreenshot` (viewport only, unless the step says `full`). It collects `Runtime.exceptionThrown` and console `error` messages and prints them per shot. It expects the dev server at `BASE` (default `http://127.0.0.1:5199/brute/`) and exits with a clear message if it is not reachable. Plain-words comments at the top explain how to use it.

`tools/screens.json` holds scenarios as data, each `{ "name": string, "steps": Step[] }` with steps `{ "save": object | null }` (writes `brute.save` in `localStorage` — `null` clears it — then reloads), `{ "eval": string }`, `{ "click": string }` (CSS selector, or `text=Some text` for a button containing that text), `{ "wait": ms }`, `{ "shot": string, "full"?: boolean }`. Start with scenarios that work on today's UI: `title`, `create`, `home` (a level-10 Veteran save), `levelup` (save with `offer` and `pendingLevelUps: 1` crossing rank 5), `prefight`, `fight` (click Start fight, wait 6 s). Build saves by taking a real `newGame(...)` result serialised to JSON — the simplest way: a scenario step that runs `eval` to create the fighter through the UI and then patches the stored save (see how the controller did it: set `character.level`, `offer`, `pendingLevelUps`). Later tasks add scenarios for their screens.

`package.json`: `"screens": "tsx tools/screens.ts"`. `.gitignore`: `screens/`.
